# INTERNAL ORDER P5 — SHARED ORDER PERSISTENCE INVENTORY

Status: READ-ONLY AUDIT of accepted runtime at P4 base. Production writers are not modified by P5.

| WRITE PATH | SOURCE OF TRUTH | INPUT VALIDATION | TRANSACTION OWNER | RISK | REQUIRED ADAPTER |
|---|---|---|---|---|---|
| `extremizer_bot.save_order_to_history()` | Runtime cart + server pricing/lookups; writes shared `orders`, `order_items`, fulfillment groups | Existing path uses coercions such as `qty=int(...)`; warehouse `customer_unit_rub=int(round(float(price_snapshot_rub)))`; route parsed through enum; warehouse_id is carried from cart/runtime selection | Self-owned `BEGIN/COMMIT` when called alone; caller-owned when `conn` supplied | Does not satisfy P4 strict pre-SQLite type contract for future Internal payment-ready persistence; browser/handoff-originated values can traverse runtime cart before persistence | Future Internal adapter must validate exact integer RUB/qty/warehouse/source/route before calling shared writer or a shared persistence primitive |
| `client_checkout_orchestrator.persist_client_checkout_atomic()` | Persisted shared order snapshots become finance source of truth | Validates callable/adapter/order ID/user/cart shape; does not itself validate every line value | **PROVEN owner:** `BEGIN IMMEDIATE -> save_order_fn(conn) -> post_persisted_order_charge(conn) -> COMMIT` | Good atomic boundary, but line validation remains delegated to writer | Reuse transaction owner; add strict Internal preparation before `save_order_fn` in future integration |
| `client_checkout_callback_adapter.execute_prepared_checkout()` | Prepared Telegram/Web handoff checkout context | Preconditions expected before adapter; delegates durable core to orchestrator | Core transaction delegated to `persist_client_checkout_atomic`; post-commit hooks are outside transaction | Must not become terms/P authority; post-commit warehouse actions cannot define immutable payment terms retroactively | Keep as runtime adapter only; Internal terms confirmation is a later separate trusted server action |
| Live `checkout_confirm` callback | Telegram user/session cart after warehouse revalidation/delivery preflight | Existing callback performs cart/warehouse availability checks and invokes `execute_prepared_checkout` | Shared core transaction via orchestrator | Existing client checkout creates request/order, not approved Internal payment-ready terms; mixed historic workflow/statuses remain | Do not wire P5 payment snapshot creation here until owner approves Internal lifecycle |
| `web_handoff.create_handoff()` | WEB cart handoff payload | Coerces `qty=int(...)`, warehouse_id=int; validates source/range; stores handoff only | Own handoff transaction | WEB payload is not financial authority and must never supply P | Handoff remains request transport; later authoritative server revalidation + strict persistence required |
| `client_order_finance_bridge.load_order_line_finance_snapshots()` / `post_persisted_order_charge()` | Persisted `order_items` | Already strict for persisted quantity/customer_unit_rub and payment_route; owner check uses `orders.telegram_user_id` | Caller-owned connection | Current owner identity is Telegram ID, not canonical future Internal Client ID | Reuse finance bridge for existing client checkout; future Internal identity adapter still required |
| `set_admin_customer_total()` | Admin manual total | Accepts numeric path and persists `float(amount_rub)` | Own transaction | Not suitable as authoritative Internal C/P; violates whole-RUB P4 boundary | Must not feed Internal payment snapshot |
| `set_admin_order_status()` and direct status callbacks | Shared `orders.status` | Allowed legacy statuses / expected-current checks vary by path | Separate transactions | Current technical statuses do not yet encode approved Internal «Собран, не оплачен» contract; some UI opening actions change `new -> working` | Owner-approved Internal status transition adapter required |
| `set_order_item_type()`, delivery-selection updates | Shared order metadata not covered by P4 terms fingerprint (item type/delivery fields) | Domain-specific validation | Separate transactions | These writes are not payment terms fingerprint fields today; safe only if they do not mutate protected fields | No P5 change |
| Direct updates to protected `order_items` fields | Shared order table | No single centralized mutation gate proven for all possible future writers | Varies | Any mutation to item ID set/source/warehouse/OEM/qty/customer_unit_rub/route after snapshot invalidates P4 proof | Future mutation service must either reject changes while active payment intent exists or trigger approved revision/supersede |

## Key audit conclusions

1. There is one proven shared order persistence path, not a second OrderEngine.
2. `persist_client_checkout_atomic()` is the correct existing transaction owner for current checkout.
3. Current production `save_order_to_history()` is **not** P4-strict at its Python input boundary because it intentionally coerces legacy cart values.
4. P5 therefore does not modify the production writer. It adds an isolated strict adapter contract that must precede any future Internal payment-ready persistence.
5. Existing `orders.telegram_user_id` is still the owner check used by current client finance; canonical Internal Client ID remains owner-open.
